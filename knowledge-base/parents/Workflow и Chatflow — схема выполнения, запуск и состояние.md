# Workflow и Chatflow: схема выполнения, запуск и состояние

Workflow и Chatflow в Dify строятся из узлов и переходов. Оба позволяют разделить задачу на этапы, передавать результаты между узлами и направлять выполнение по разным веткам. Различие проявляется в режиме запуска и в том, какое состояние доступно следующему запуску.

## Как выполняются Workflow и Chatflow

Каждый узел отвечает за отдельный шаг: вызов модели, поиск данных, выполнение кода или выбор ветки. Например, Question Classifier классифицирует ввод и направляет его по подходящему маршруту.

Для HTTP Request можно настроить fallback-ветку. Если внешний API недоступен, схема продолжит выполнение по альтернативному пути.

## Как запускаются Workflow и Chatflow

Workflow выполняется один раз от входных данных до результата. Его может запустить пользователь или Trigger: по расписанию, с заданным интервалом, через webhook либо по событию интеграции.

В Chatflow каждое сообщение пользователя запускает спроектированную схему до формирования ответа. Несколько таких запусков могут относиться к одной chat session.

## Что сохраняется между запусками Workflow и Chatflow

Обычные workflow variables существуют только во время одного выполнения и сбрасываются после его завершения. Поэтому независимый запуск Workflow не получает промежуточные значения предыдущего запуска.

В Chatflow conversation variables сохраняются между сообщениями одной chat session. Они позволяют переносить состояние внутри конкретного диалога; другая сессия получает отдельное состояние.

Логи Workflow тоже сохраняются: в них доступны входы, выходы, статус, расход токенов и трассировка узлов. Однако лог нужен для наблюдения и разбора. Следующий запуск не получает его содержимое автоматически как рабочие переменные.

| Механизм | Область действия | Что доступно следующему запуску |
|---|---|---|
| Workflow variables | Одно выполнение | Ничего: значения сбрасываются |
| Conversation variables | Одна chat session | Состояние, записанное в переменные этой сессии |
| Workflow logs | История запусков приложения | Доступны для просмотра, но не передаются в выполнение автоматически |

## Как агентские узлы работают с данными между запусками

В Chatflow параметр Memory у Classic Agent node передаёт модели предыдущие сообщения текущего диалога. В обычном Workflow история по `conversation_id` не загружается: агент работает с задачей и данными текущего запуска. Его итерации сохраняют контекст внутри этой задачи, но не создают память между независимыми запусками.

New Agent здесь рассматривается только как этап Workflow, вызываемый через Agent node. Каждый вызов начинает работу в отдельном sandbox из сохранённой конфигурации агента. Файлы, программы и другие изменения, созданные только во время выполнения, в следующий запуск не переносятся. Нужные последующим узлам результаты следует объявить выходами Agent node и явно передать дальше по схеме.

Таким образом, агентский узел сам по себе не ведёт общую историю заданий разных пользователей и запусков.

## Как сохранить состояние между запусками Workflow

Из ограничений Workflow следует архитектурный вывод: если процесс должен помнить пользователя, задачу или результат предыдущего запуска, состояние нужно вынести во внешнее хранилище.

Workflow должен получить устойчивый идентификатор пользователя или задачи, прочитать связанное состояние через Tool node или HTTP Request, использовать его и записать обновление обратно. Выбор хранилища и способ интеграции зависят от проекта: это явно спроектированный обмен данными, а не встроенная память Workflow.
