# Тестирование, логи и эксплуатация AI-приложения в Dify

Качество AI-приложения нельзя оценить по одному тестовому сценарию. Сначала отдельные случаи используют для поиска и исправления конкретных проблем. Затем изменение проверяют на наборе сценариев, чтобы убедиться, что оно не ухудшило поведение приложения в других ситуациях.
Dify помогает разбирать и повторно проверять отдельные случаи. Для систематической оценки на наборе сценариев данные из Dify можно передавать во внешнюю eval-систему.

## Как улучшать качество ответа AI-приложения

Если результат не соответствует ожиданию, работа строится как последовательный цикл:

1. Воспроизвести отклонение на том же входе.
2. Определить, на каком шаге фактическое выполнение разошлось с ожидаемым.
3. Выбрать предполагаемую причину: prompt, данные, переменную, узел или настройку retrieval.
4. Внести изменение и повторить исходный сценарий.
5. Убедиться, что конкретное отклонение устранено.
6. Проверить изменение на наборе других сценариев и найти возможные регрессии.

Первые пять шагов помогают исправить конкретный случай. Последний показывает, улучшилось ли поведение приложения в целом, а не только на одном примере.

Это экспертная методика, собранная на основе доступных инструментов Dify. Документация не представляет её как встроенный автоматический алгоритм поиска причины.

## Какие данные нужны для диагностики AI-приложения

Для разбора запуска недостаточно смотреть только на финальный текст. Нужны:

- вход и итоговый результат;
- порядок выполнения узлов;
- промежуточные данные;
- использованный контекст и вызовы tools;
- ошибки и статус;
- длительность;
- расход токенов.

Доступность конкретных данных зависит от типа приложения:

- для Chatflow логи показывают трассировку сообщения по узлам;
- для Workflow доступны исходный ввод, итоговый вывод, результат и статус, расход токенов, metadata, порядок и время выполнения узлов и движение данных;
- сессии New Agent из собственного web app и из Workflow собираются на странице Logs агента с указанием источника. В диалоге можно изучить сообщения, расход токенов, задержку и итерации вызова tools; вызов из Workflow также входит в трассировку общего запуска;
- для Legacy Agent app доступны исходный prompt и итерации вызова функций.

## Как Dify помогает разобрать отдельный запуск

### Workflow

До публикации весь сценарий запускают через Test Run. Отдельный узел можно проверить изолированно и изучить его входы, выходы, длительность и ошибки в Last run. Variable Inspector показывает промежуточные данные и позволяет подставить изменённое значение в последующие узлы без полного перезапуска схемы.

После публикации Logs фиксируют запуски из web app, API и triggers. Для воспроизведения production-случая функция Test With Params повторно запускает Workflow в редакторе с теми же входными параметрами.

### Chatflow

Узлы Chatflow проверяют теми же инструментами отдельного запуска и Variable Inspector. После публикации Logs позволяют открыть весь диалог и трассировку конкретного сообщения по узлам, посмотреть расход токенов и задержку. Сессии Preview в эти логи не попадают, поэтому при настройке используют данные Last run, а опубликованные обращения разбирают в Logs.

### New Agent

Настроенного New Agent до публикации проверяют в Preview: этот режим показывает поведение, которое увидит конечный пользователь, но не меняет конфигурацию агента. Сессии опубликованного агента собираются на его странице Logs с указанием источника — собственный web app или Workflow. Там можно открыть переписку, посмотреть расход токенов, задержку и итерации вызова tools.

Если New Agent вызван из Workflow, его сессия видна в Logs агента, а место этого вызова — в трассировке общего Workflow. Step Run и Variable Inspector относятся к визуальной схеме Workflow и Chatflow, а не к самостоятельному New Agent.

## Мониторинг опубликованного приложения

После публикации Dify помогает не только разбирать уже известный случай, но и находить обращения, которые требуют проверки.

Dashboard показывает динамику объёма сообщений, активных пользователей, среднего числа взаимодействий и расхода токенов. Эти показатели описывают использование приложения, но сами по себе не показывают, был ли конкретный ответ правильным.

В Logs сохраняются реальные обращения из web app, API и triggers. **User Rate** отражает реакции конечных пользователей — like, dislike и оставленный с dislike комментарий. **Op. Rate** показывает оценки, которые участники команды поставили ответам при просмотре логов. Эти сигналы помогают выбирать случаи для разбора, но не заменяют критерии качества и проверку результата.

Если для проблемного вопроса подготовлен правильный ответ, его можно сохранить вместе с вопросом в Annotation System. При семантически похожем обращении Dify вернёт этот ответ вместо новой генерации. Это точечное покрытие группы похожих вопросов, а не общее улучшение модели или приложения. История попаданий показывает, какие annotations срабатывают и какие темы стоит покрыть дополнительно.

## Автоматизированная оценка AI-приложения

Dify умеет передавать наблюдаемость во внешние платформы, включая Langfuse и LangSmith. Интеграция Langfuse подключается в настройках мониторинга конкретного приложения и получает данные из отладки и production. Для этого не требуется вручную вызывать API трассировки для каждого теста.

Автоматизированная оценка строится как повторяемый цикл:

1. сформировать датасет сценариев;
2. определить критерии и evaluators;
3. запускать оценку на одном и том же наборе;
4. сравнивать результат с базовой версией;
5. находить конкретные регрессии;
6. принимать решение о выпуске.

В Langfuse датасеты содержат входы и ожидаемые выходы. Тест-кейсы можно формировать из production-трасс и запускать до выпуска. Качество результата оценивается вручную, программно или моделью по заданному критерию. На одинаковых кейсах можно сравнивать изменения prompt, модели, retrieval или кода.
