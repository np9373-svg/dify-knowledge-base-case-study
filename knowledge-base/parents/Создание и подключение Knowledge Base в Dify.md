# Создание и подключение Knowledge Base в Dify

Сначала нужно решить, кто будет управлять базой знаний. Базу можно сформировать средствами Dify либо оставить во внешней RAG-системе и подключить к приложению через API.

Если базой управляет Dify, есть ещё один выбор: использовать готовую обработку документов или собрать собственный Knowledge Pipeline.

`Dify управляет базой → готовая обработка или собственный pipeline`

`Внешняя система управляет базой → подключение через External Knowledge API`

## Когда базой управляет Dify

В обоих вариантах данные проходят подготовку, превращаются в chunks и попадают в Knowledge Base, которую затем можно использовать для поиска. Отличается степень контроля над подготовкой данных.

### Готовая обработка

Самый короткий путь — загрузить данные и использовать стандартную обработку Dify. Источником могут быть локальные файлы; после загрузки документы обрабатываются и индексируются, поэтому становятся доступны для поиска не мгновенно.

Документы делятся на **chunks** — отдельные фрагменты содержимого, с которыми затем работает поиск. При создании базы выбирают структуру chunks и параметры обработки. Этот вариант подходит, если стандартной подготовки документов достаточно.

### Собственный Knowledge Pipeline

Knowledge Pipeline — визуальная схема формирования базы:

`источник → извлечение и преобразование → chunker → Knowledge Base node → тестирование и публикация`

Pipeline позволяет выбрать источники, extractor, преобразования и способ нарезки. Источниками могут быть файлы, онлайн-документы, облачные диски и веб-краулеры; дополнительные источники доступны через Marketplace. В Knowledge Base node задаются структура chunks, индексация и настройки поиска.

## Что задаётся при формировании базы в Dify

Независимо от способа подготовки нужно определить, как содержимое будет разделено на chunks и в какой структуре они попадут в Knowledge Base.

Алгоритм нарезки chunks определяет, **где провести границы фрагментов**. Структура базы определяет, **в каком виде Dify сохранит и будет возвращать результат**.

Встроенная Knowledge Base использует одну из трёх структур:

- **General** — найденный chunk возвращается напрямую;
- **Parent-child** — поиск выполняется по небольшим дочерним chunks, а модели передаётся более широкий родительский контекст;
- **Q&A** — индексируется вопрос из пары «вопрос — ответ», а при совпадении возвращается связанный ответ.

В собственном pipeline можно применять разные алгоритмы и обработчики, но результат для Knowledge Base node всё равно должен соответствовать одной из этих структур. После сохранения и публикации переключить структуру нельзя; изменение параметров внутри неё требует переиндексации.

### Metadata документов

Metadata добавляют к документам признаки, по которым впоследствии можно ограничивать область поиска. Dify поддерживает встроенные поля `document_name`, `uploader`, `upload_date`, `last_update_date` и `source`. По умолчанию они отключены; после включения Dify формирует их значения для существующих и новых документов.

Пользователь может создавать собственные поля типов string, number и time и назначать их значения отдельным документам или группе документов. Набор полей задаётся на уровне Knowledge Base, а значения могут различаться у каждого документа.

## Когда базой управляет внешняя система

Если собственная RAG-система уже существует, её можно подключить через External Knowledge API. Внешняя система сама хранит документы, строит индекс и выполняет поиск. Dify отправляет запрос и получает найденные chunks с оценками и metadata.

Это не импорт базы в Dify: платформа имеет retrieval-доступ к результатам, но не управляет содержимым, индексом или схемой metadata внешней системы. Внешний endpoint может вернуть вместе с каждым chunk произвольные пары ключ–значение, которые Dify сохранит в результате поиска.

## Как выбрать вариант Knowledge Base в Dify

- Если хранением и поиском должен управлять Dify, выберите готовую обработку или Knowledge Pipeline.
- Готовая обработка подходит, когда достаточно стандартной загрузки и нарезки документов.
- Knowledge Pipeline нужен, когда требуется собственная последовательность источников, извлечения, преобразования и нарезки.
- External Knowledge подходит, когда хранение, индексирование и поиск уже выполняет внешняя система.
