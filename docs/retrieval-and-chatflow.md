# Retrieval и Chatflow

## Схема приложения

```text
Start → Knowledge Retrieval → LLM → Answer
```

Вопрос пользователя без предварительной классификации передаётся в Knowledge Retrieval. Найденные родительские документы поступают в context LLM. Модель формирует ответ, а Dify показывает Citations.

## Активные настройки Knowledge Base

| Параметр | Значение |
| --- | --- |
| Chunk Structure | Parent-Child |
| Embedding model | `text-embedding-3-small` |
| Retrieval method | Vector Search |
| Top K | 3 |
| Rerank model | Disabled |
| Score threshold | Disabled |
| Full-Text Search | Disabled |
| Child separator | `@@CHILD@@` |

## Почему без Full-Text Search

Ассистент помогает понять концепции и выбрать вариант решения. Пользователи формулируют одину и ту же задачу по-разному, поэтому семантический поиск здесь важнее точного совпадения терминов. В тестах Full-Text Search не дал полезного улучшения.

Это решение не является универсальным. Для кодов ошибок, API-полей, редких имён и точных технических терминов гибридный поиск может оказаться лучше.

## Почему без reranking

При `Top K = 3` поиск обычно возвращает два полезных родителя. Один из них может содержать избыточный контекст, но в данном корпусе это не мешает модели отвечать. Дополнительный reranking не решал наблюдаемую проблему, поэтому он отключён.

## О поле `multiple_retrieval_config` в YAML

Экспорт `app.yml` может содержать сериализованный блок `multiple_retrieval_config` с моделью reranking и другим `top_k`. Он не описывает активную конфигурацию единственной подключённой Knowledge Base. Фактические активные настройки показаны в интерфейсе Knowledge Base и на скриншоте [`assets/knowledge-settings.png`](../assets/knowledge-settings.png).

Редактировать этот служебный блок вручную не следует.

## Почему этого достатно

Сложность retrieval должна отвечать на наблюдаемую ошибку. Если качество уже достаточно, добавление ещё одной модели или метода поиска не является самоцелью.
