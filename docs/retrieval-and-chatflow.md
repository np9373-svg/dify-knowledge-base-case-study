# Retrieval и Chatflow

## Схема приложения

```text
Start → Knowledge Retrieval → LLM → Answer
```

Вопрос пользователя без предварительной классификации передаётся в Knowledge Retrieval. Найденные родительские документы поступают в context LLM. Модель формирует ответ, а Dify через Citations показывает документы Knowledge Base, использованные при ответе.

## Активные настройки Knowledge Base

| Параметр | Значение |
| --- | --- |
| Chunk Structure | Parent-Child |
| Embedding model | `text-embedding-3-small` |
| Retrieval method | Vector Search |
| Top K | 3 |
| Rerank model | Disabled |
| Score threshold | Disabled |
| Full-Text Search | Disabled |
| Child separator | `@@CHILD@@` |

## Почему без Full-Text Search

Ассистент помогает понять концепции и выбрать вариант решения. Пользователи формулируют одну и ту же задачу по-разному, поэтому здесь важнее смысловая близость запроса и фрагмента, а не совпадение отдельных слов. Для такого корпуса достаточно векторного поиска.

Full-Text Search был бы полезнее в технической базе с кодами ошибок, API-полями, редкими именами и устойчивыми терминами. В этом проекте поиск по словам не улучшал ответы и мог добавлять фрагменты, совпадающие с запросом лексически, но не относящиеся к решению пользователя. Поэтому он отключён.

## Почему без reranking

При `Top K = 3` поиск чаще всего возвращает два подходящих родительских документа. Иногда один из них содержит избыточный контекст, но это не мешает модели сформировать ответ. Благодаря качественно спроектированной базе знаний качество уже оказалось достаточным без reranking, поэтому отдельная модель ранжирования не потребовалась.

## Почему простой конфигурации достаточно

Основная сложность проекта сосредоточена в структуре и содержании базы знаний. Когда дочерние чанки хорошо находятся по смыслу, а родительские документы дают связный и релевантный контекст, дополнительное усложнение retrieval не улучшает решение пользовательской задачи.
