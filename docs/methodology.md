# Методология

База знаний создавалась не как копия документации Dify, а как ограниченный и проверяемый источник знаний для конкретных пользовательских задач.

Данные базы знаний формируются с учётом структуры Parent-Child.
В этом проекте один и тот же материал должен помогать отвечать на разные вопросы о Dify: пользователь может по-разному сформулировать задачу, а для рекомендации часто нужен контекст из нескольких связанных аспектов темы. Поэтому для базы выбрана структура Parent-Child: поиск выполняется по конкретным дочерним разделам, а модель получает семантически целостный родительский документ.
Структура Q&A менее подходит для проекта, так как она позволяет эффективно извлекать данные в случае набора независимых вопросов со стабильными формулировками и самостоятельными ответами.

Подробнее различия между подходами и физическая структура документов описаны в [архитектуре базы знаний](knowledge-architecture.md).

Ниже описаны этапы формирования базы знаний. Это позволяет повторить подход при актуализации и расширении знаний.

## 1. От задач пользователя к вопросам

Работа началась с описания аудитории, её болей и вопросов. Для каждого вопроса фиксировались:

- короткая пользовательская формулировка;
- боль или решение, которое стоит за вопросом.

Этот набор стал первым исследовательским толчком: техническим заданием, картой предполагаемого покрытия и источником вопросов для тестирования.

## 2. Сбор атомарных фактов

В реестр попадали только факты, нужные для ответа на выбранные вопросы. Для каждого факта сохранялись:

- исходная формулировка;
- перевод;
- редакторская формулировка для базы, так чтобы факт был самодостаточным без контекста;
- ссылка на официальный источник.

Целью было не покрыть всю документацию Dify, а ограничить корпус данными, нужными ассистенту.

## 3. От фактов к темам

Темы не задавались заранее. Они появлялись по мере сбора и сопоставления фактов. Такой порядок помог не навязывать материалу слишком раннюю рубрикацию.

На данном этапе появляются прототипы родителей и сопоставление родителей с фактами.

## 4. Проектирование родителей

Родитель отвечает на один основной вопрос. Критерии помогают проверить границы родителя:

1. Вся ли информация относится к одной сущности или одному решению?
2. Нужна ли большая часть родителя для понимания каждого дочернего раздела?
3. Не окажется ли 70–80% возвращённого модели текста посторонним для детального вопроса?
4. Можно ли обновлять этот материал как одну смысловую единицу?
5. Можно ли однозначно назвать основной вопрос родителя?

Если родитель отвечает на несколько независимых основных вопросов или большинство его разделов не нужны друг другу, его следует разделить. Если соседние родители постоянно нужны вместе и обновляются одновременно, стоит проверить, не раздроблена ли тема слишком мелко.

В процессе также происходит уточнение формулировок фактов, добавление новых фактов и актуализация сопоставления.

## 5. Написание статей

Статьи писались не как пересказ фактов, а как связное, лаконичное объяснение. В процессе повторно проверялись:

- границы родителя;
- достаточность контекста;
- связность дочерних разделов;
- отсутствие неподтверждённых утверждений.

## 6. Финальная физическая структура

- один родитель — один Markdown-документ;
- один дочерний чанк — один смысловой раздел;
- дочерние чанки явно разделены `@@CHILD@@`.
- объём дочерних чанков — 1500–2000 символов.

## 7. Настройка базы знаний в Dify

Выбрана конфигурация:

- Vector Search;
- `Top K = 3`;
- без reranking;
- без Full-Text Search;
- без score threshold.

## Обновление базы

Обновление — продолжение того же метода:

1. Собрать новые или неудачные вопросы.
2. Проверить, находится ли проблема в retrieval, в исходных знаниях или в формировании ответа.
3. Если не хватает знаний, найти и проверить новые официальные факты.
4. Обновить существующий родитель или создать новый, если смысловые границы изменились.
5. Повторить Retrieval Testing.
